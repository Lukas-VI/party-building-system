# 团队协作与测试服部署流程本文说明当前项目的团队协作、VPN 访问、共享测试服、个人分支调试和自动部署规则。## 1. 环境角色### GitHub 仓库- 仓库：`https://github.com/Lukas-VI/party-building-system`- `main` 分支是共享测试服的自动部署基准分支。- 团队成员日常开发应从 `main` 拉新分支，不直接在 `main` 上写未验证代码。### 远端 Ubuntu 测试服务器- 服务器系统：Ubuntu 26.04- 项目目录：`/opt/party-building-mini-app`- 运行用户：`havensky`- VPN 静态 IP：`192.168.66.228`- SSH 只通过 VPN 访问：```bashssh havensky@192.168.66.228```### 公网验收入口- 前端统一入口：`http://39.105.127.142:1919/web-admin/`- API 健康检查：`http://39.105.127.142:1145/api/health`- SSH 不通过 frp 暴露公网。## 2. VPN 使用规则团队成员需要先连接 OpenVPN，再访问服务器 SSH。当前推荐的 OpenVPN 策略：- 使用 Split-Tunnel，避免接管团队成员本机全部互联网流量。- 服务器静态 VPN IP 固定为 `192.168.66.228`。- Access Rules 需要允许团队客户端访问 `192.168.66.228/32`，或允许服务器静态网段 `192.168.66.0/24`。- 如团队成员互访服务器失败，需要启用 InterClient Communication 或等价的 client-to-client 访问能力。验证 VPN 是否可用：```bash ping 192.168.66.228 ssh havensky@192.168.66.228```## 3. 自动部署规则远端服务器已安装 systemd timer：```bashparty-building-auto-deploy.timerparty-building-auto-deploy.service```自动部署脚本位置：```bash/opt/party-building-mini-app/scripts/auto-deploy-main.sh```执行逻辑：1. 每分钟检查一次 `origin/main`。2. 如果服务器本地 `main` 与 `origin/main` 一致，则不做任何事。3. 如果 `origin/main` 比服务器本地 `main` 新，且是快进关系，则自动：   - checkout 最新 `main`   - 安装缺失依赖   - 构建 PC 后台   - 构建服务号 H5   - 重启 PM2 服务   - 验证 API 与前端网关4. 如果服务器本地 `main` 领先 `origin/main`，脚本会跳过，等待 GitHub 追上，避免把测试服回退。5. 如果出现分叉，脚本会报错并停止，需人工处理。查看自动部署状态：```bashsystemctl status party-building-auto-deploy.timerjournalctl -u party-building-auto-deploy.service -n 80 --no-pager```手动触发自动部署检查：```bashsudo systemctl start party-building-auto-deploy.service```## 4. 日常开发流程### 开始一个功能```bashgit checkout maingit pull origin maingit checkout -b feature/your-feature-name```分支命名建议：- `feature/mobile-workflow`- `feature/org-admin`- `fix/login-cors`- `docs/deploy-guide`### 本地提交```bashgit statusgit add <files>git commit -m "Describe the change"```### 推送个人分支```bashgit push -u origin feature/your-feature-name```### 合并到 main建议通过 Pull Request 合并到 `main`。合并后，测试服会自动发现 `origin/main` 有新提交并部署。## 5. 个人分支远端调试共享测试服默认跟随 `main`。如果某个成员需要把个人分支临时部署到远端测试服，可以手动执行：```powershell.\scripts\deploy-to-ubuntu.ps1 -Branch feature/your-feature-name```注意：- 这会临时占用共享测试服。- 调试结束后应切回 `main`：```powershell.\scripts\deploy-to-ubuntu.ps1 -Branch main```更推荐的做法：1. 个人分支本地开发。2. 必要时短时间手动部署个人分支。3. 验证完成后合并到 `main`。4. 让自动部署负责共享测试服的正式更新。## 6. 测试服健康检查公网检查：```bashcurl http://39.105.127.142:1145/api/healthcurl -I http://39.105.127.142:1919/web-admin/```服务器本机检查：```bashssh havensky@192.168.66.228pm2 listcurl http://127.0.0.1:3000/api/healthcurl -I http://127.0.0.1:1919/web-admin/systemctl is-active frpc.servicesystemctl is-active openvpn-client@profile-autologin```## 7. 常见情况### 日志显示 local main is ahead of origin/main含义：服务器上的 `main` 比 GitHub `origin/main` 新。通常原因：- 使用本地 bundle 手动部署过尚未推送到 GitHub 的提交。处理方式：- 将本地提交推送到 GitHub。- 或保持现状，自动部署会跳过，不会回退测试服。### 日志显示 remote main is not a fast-forward含义：服务器本地 `main` 和 GitHub `origin/main` 分叉。处理方式：1. 暂停自动部署：```bashsudo systemctl stop party-building-auto-deploy.timer```2. 人工确认应保留哪边提交。3. 修复分支历史后重新启用：```bashsudo systemctl start party-building-auto-deploy.timer```### 连 VPN 后不能上网OpenVPN 客户端被配置成 Full-Tunnel。处理方式：- 在 OpenVPN Admin 中将 Internet Access 改为 Split-Tunnel。- 保留访问 `192.168.66.228/32` 或 `192.168.66.0/24` 的规则。### 连 VPN 后不能 SSH 服务器检查：- 本机是否连上 VPN。- 是否能 ping `192.168.66.228`。- OpenVPN Access Rules 是否允许访问 `192.168.66.228/32`。- 是否启用了客户端互访能力。## 8. 当前服务清单远端服务器主要服务：```textopenvpn-client@profile-autologin  VPN 客户端，获取 192.168.66.228frpc.service                      frp 客户端，暴露 Web/APIpm2-havensky.service              PM2
